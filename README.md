## 定位

市面上的麦当劳 Skill 都在回答"怎么点最省/怎么点最健康"。
我们回答一个更完整的问题：**"一群 agent 怎么协作帮你点餐"**。

正如麦当劳官方所说：**"帮助 AI Agent 连接麦当劳服务"**、
**"集成点餐、领券等核心能力，快速构建拥有麦当劳能力的专属 AI Agent"**——
我们在此基础上，加入**多 agent 协作**与**治理层**：
不是"一个 agent 帮你点餐"，而是"一群 agent 协作，owner 审批后安全下单"。

## 核心设计

### 角色分工（多 agent 协作）

| Agent | 角色 | 职责 |
|---|---|---|
| **营养师** | 健康守门员 | 分析营养构成，标记超标项 |
| **预算师** | 省钱专家 | 计算最优组合，暴露凑单陷阱 |
| **口味师** | 美食顾问 | 推荐搭配，考虑个人偏好 |
| **owner（你）** | 最终决策者 | 审批方案，确认下单 |

### 治理层（两本账）

- **需求账**：你想吃什么（口味/营养/份量）
- **预算账**：你愿意花多少钱（预算/券/积分）
- **审批链**：三 agent 出方案 → owner 审批 → 安全下单

### 与冠军仓的差异

| | mcd-coupon-strategist | mcd-agent-gourmet（我们） |
|---|---|---|
| 视角 | 单 agent 省钱 | **多 agent 协作** |
| 决策 | 算法排序 | **角色分工+owner 审批** |
| 输出 | 最优方案 | **多方案对比+推荐理由** |
| 治理 | 无 | **两本账+审批链** |

### 治理层（两本账）

**需求账**：
- 你想吃什么（口味/营养/份量）
- 你的预算上限
- 你的券/积分存量

**预算账**：
- 当前方案实付金额
- 券的沉默成本（即将过期的券）
- 积分价值（积分兑换 vs 现金支付）

**审批链**：
```
三 agent 出方案 → 协调器汇总 → owner 审批 → 安全下单
     ↓                ↓            ↓           ↓
  营养师报告      对比表生成    显式确认    create-order
  预算师方案      标注冲突点    价格复核    返回支付链接
  口味师推荐      推荐理由      最终决策    query-order 确认
```

### 与单 agent 方案的差异

| 维度 | 单 agent（如 mcd-coupon-strategist） | 多 agent（我们） |
|---|---|---|
| **决策模式** | 算法排序 → 输出最优解 | 角色分工 → owner 审批 |
| **输出形式** | 单一方案 | 多方案对比+推荐理由 |
| **冲突处理** | 算法内部权衡 | 显式标注冲突点（如"营养超标但最便宜"） |
| **治理** | 无 | 两本账+审批链 |
| **可解释性** | "这是最省的" | "营养师推荐 A（健康），预算师推荐 B（省钱），你选哪个？" |

### 七条铁律（约束式 Prompt Engineering）

1. **绝不猜测价格** —— 所有金额来自 MCP `calculate-price` 返回
2. **先确定门店** —— 价格与券可用性均绑定门店
3. **多 agent 意见必须呈现** —— 不强行统一，如实展示差异
4. **owner 审批是硬门** —— 任何下单操作必须经 owner 显式确认
5. **主动暴露凑单陷阱** —— 为用券加购导致实付上升必须指出
6. **不确定就说不确定** —— 缺货/价格缺失如实说明
7. **不构成营养或医疗建议** —— 仅作为参考信息呈现

### 适配层模式

所有 MCP 响应经 `mcd_adapter.py` 统一转换后才进业务逻辑——
**全员唯一的"分→元"换算点**，防止单位混乱。

```python
# 错误：业务逻辑里直接换算（会导致单位混乱）
price = meal["price"] / 100  # 分→元

# 正确：适配层统一换算（全员唯一入口）
from mcd_adapter import cents_to_yuan
price = cents_to_yuan(meal["price"])
```
